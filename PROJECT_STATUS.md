# Kerfuffle — статус проекта

## Готово

- FastAPI, PostgreSQL, Alembic и React/Vite/TypeScript.
- Встроенная авторизация: Argon2id-пароли, HttpOnly cookie-сессии, CSRF,
  проверка источника запросов и rate limiting.
- CLI для создания первого суперпользователя; приглашения организаторов и
  восстановление пароля по одноразовым ссылкам с истечением срока действия.
- Управление пользователями, блокировкой организаторов и назначениями
  мероприятий. Исторические внешние identity IDs сохраняются как
  `legacy_identity_subject` и не используются для входа.
- Короткие коды регистратора и площадки остаются отдельными от учетных
  записей и работают с ограниченными серверными сессиями.
- Keycloak/OIDC удалены из активного приложения, Compose-конфигурации,
  frontend-зависимостей и setup-документации.
- Обновлены инструкции корня проекта, backend, frontend и Docker Compose.
- Production settings требуют HTTPS origins, SMTP, сильный секрет кодов,
  отдельную runtime DB-роль и PostgreSQL TLS.
- Публичный рейтинг и организаторский журнал исправлений/аннулирований с
  обязательной причиной и неизменяемым аудитом.
- QR-генерация, QR-поиск и QR-поля удалены из активного приложения. Миграция
  `0007_nullable_legacy_qr_token` сохраняет старые значения, но разрешает
  создавать регистрации без QR; физическое удаление колонки отложено.
- Создание мероприятия и начисление через аккаунт используют cookie-сессию
  без обязательного bearer token.
- Маршрутные листы содержат набор площадок без фиксированного порядка.
  Регистратор выбирает лист при регистрации; вместимость может быть
  неограниченной. Начисление разрешено только на площадке из листа участника.

## Проверки и состояние данных

- Backend: 81 тест пройден; отдельно на временной PostgreSQL прошёл
  concurrency-тест маршрутной вместимости. Осталось стороннее предупреждение
  Starlette/httpx.
- Frontend: 5 regression-тестов пройдены; lint, TypeScript type-check и
  production build пройдены.
- `npm audit` сообщил о 6 high уязвимостях в dev-зависимостях сборки и
  тестирования; `npm audit --omit=dev` сообщил 0 уязвимостей. Предложенное
  автоматическое исправление требует major downgrade Vite, поэтому оно не
  применялось без отдельной проверки совместимости.
- Alembic head — `0008_route_sheets`; полная цепочка миграций успешно применена
  к отдельной временной PostgreSQL. Там же проверены триггеры ограничения
  начисления площадками маршрутного листа и изменения назначенного листа.
  Рабочая локальная БД обновлена до `0008_route_sheets`; case-insensitive
  дубликатов email не было, количество строк в существующих таблицах не
  изменилось. Перед обновлением создана и проверена резервная копия.
  Миграционный запуск завершился успешно от имени владельца схемы.
- PostgreSQL-конкурентный regression-тест использует только отдельную тестовую
  БД через `KERFUFFLE_TEST_POSTGRES_URL`; он выполнен успешно на временном
  изолированном кластере, который после проверки остановлен и удалён.
- SQL миграции `0008` отдельно сгенерирован offline без подключения к БД.
  Полная генерация SQL для старой цепочки останавливается на существующей
  миграции `0002_six_digit_ids`, использующей `Connection.scalar` с offline
  `MockConnection`.
- `0006` сохраняет старые identity IDs и данные мероприятий, участников и
  начислений; добавляет локальные auth-таблицы и прекращает требовать внешний
  subject для аккаунта. Миграция остановится при дублирующихся email без учёта
  регистра.
- Compose startup применяет миграции автоматически. Перед обновлением
  существующей установки необходимо сделать и проверить резервную копию.
- Docker CLI в текущем окружении не установлен; сборка Compose не проверена.
  Архив `mustiness-kerfuffle-package.zip` после удаления Keycloak
  и замены авторизации ещё не пересобирался.
- SMTP end-to-end не проверен: для этого нужны SMTP-реквизиты. В локальной
  разработке superuser может получить ссылку приглашения/сброса в интерфейсе.

## Необходимо до минимального production-релиза

1. Выбрать хостинг, домен, TLS/reverse proxy и подготовить staging на той же
   платформе.
2. Настроить SMTP, секреты в secret manager и процедуры блокировки,
   восстановления и ротации аккаунтов.
3. Создать production PostgreSQL в приватной сети, отдельную runtime-роль и
   migration job с владельцем схемы.
4. Настроить автоматические шифрованные бэкапы и провести пробное
   восстановление.
5. Настроить ingress rate limiting/trusted proxy и проверить эффективный IP
   клиента за reverse proxy.
6. Провести сквозные acceptance-тесты на staging: приглашение организатора,
   смена/сброс пароля, регистрация, начисление, гонка повторного начисления,
   отзыв staff-кода и действующей сессии, корректировка/аннулирование и рейтинг.
7. Утвердить privacy notice, сроки хранения персональных данных, процесс
   удаления/экспорта данных и владельца реакции на инциденты.
8. Собрать новый переносимый ZIP и проверить его содержимое; Compose build и
   запуск проверить на машине с Docker Desktop.

## Следующие шаги

1. Вернуть в `backend/.env` роль приложения `kerfuffle_app` для обычного запуска
   приложения; не оставлять runtime-подключение от имени владельца схемы.
2. Проверить полный пользовательский сценарий локально: первый superuser,
   приглашение/активация, назначение мероприятия, короткие коды сотрудников и
   восстановление пароля.
3. Настроить SMTP для реальной доставки приглашений и восстановления.
4. Пересобрать и протестировать пакет на машине с Docker Desktop.
