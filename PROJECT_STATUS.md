# Kerfuffle — статус проекта

Последнее обновление: 12 ноября 2026 г.

## Готово

- FastAPI, PostgreSQL, Alembic и React/Vite/TypeScript.
- Keycloak OIDC/PKCE: роли системного администратора и организатора.
- Системный администратор создаёт организатора через Keycloak service account
  с ролью `manage-users`; одноразовый временный пароль нужно сменить при
  первом входе.
- Организатор создаёт мероприятия и площадки, настраивает шкалу баллов,
  выпускает и отзывает коды регистратора и коды с привязкой к площадке.
  Подпись, введённая организатором, является кодом входа: 8–16 символов из
  удобного алфавита, без неоднозначных `I/O/0/1`.
- Регистрация и начисление по коду работают через ограниченные серверные
  сессии; секреты кодов хранятся как HMAC-хеши. Проверки доступа, шкалы и
  уникальности начислений остаются на сервере и в БД.
- Публичный рейтинг и организаторский журнал исправлений/аннулирований с
  обязательной причиной и неизменяемым аудитом.
- Миграция `0005_scoped_access_codes` применена к локальной PostgreSQL;
  runtime-роль может читать/изменять данные, но не создавать объекты.
- В production режиме backend требует HTTPS OIDC/Keycloak, отдельную DB-роль,
  PostgreSQL TLS, длинный секрет кодов и отключённый bootstrap admin.
  API-ответы `no-store`; Swagger/OpenAPI отключены.
- Production minimum и локальные инструкции записаны в README проекта.
- Добавлен локальный Docker Compose-пакет для Windows: frontend, backend,
  PostgreSQL, Keycloak и автоматические миграции. Секреты генерируются при
  первом старте в игнорируемом `deploy/.env`.
- Подготовлен transfer-архив `mustiness-kerfuffle-package.zip`; его состав
  проверен на отсутствие `.env`, виртуальных окружений и `node_modules`.
- Нижняя подпись интерфейса изменена на `mustiness`.

## Проверки

- Backend: последний полный запуск — 63 теста пройдены.
- Frontend build и lint прошли; Vite proxy подключён к backend на `8001`.
- Docker/Podman отсутствуют в текущем окружении, поэтому Compose build и
  запуск контейнеров здесь ещё не проверены; их нужно проверить на машине с
  Docker Desktop.
- Проверены PostgreSQL health, миграция и доступность Keycloak service account.
- Ключи/пароли локальной разработки находятся в игнорируемом `backend/.env`.
  Не переносить их в репозиторий или production.

## Необходимо до минимального production-релиза

**Блокирующее:**

1. Выбрать хостинг, домен, TLS/reverse proxy и способ публикации frontend/API;
   подготовить staging на той же платформе.
2. Настроить production Keycloak: HTTPS, MFA для администраторов, brute-force
   защиты, восстановление доступа, роли service account и сроки сессий.
3. Создать production PostgreSQL в приватной сети, отдельную runtime-роль,
   секреты в secret manager и миграционный job с владельцем схемы.
4. Настроить автоматические шифрованные бэкапы и провести пробное
   восстановление.
5. Настроить ingress rate limiting/trusted proxy и проверить эффективный IP
   клиента за production reverse proxy. Текущий кодовый лимитер считает IP из
   соединения, поэтому прокси должен быть настроен осознанно.
6. Провести сквозные acceptance-тесты на staging: создание организатора и
   смена пароля; регистрация; поиск/начисление; гонка повторного начисления;
   отзыв кода с уже открытой сессией; корректировка/аннулирование и рейтинг.
7. Утвердить privacy notice, сроки хранения персональных данных, процесс
   удаления/экспорта данных и владельца реакции на инциденты.

**До запуска также желательно:**

- Мониторинг доступности, ошибок и БД, алерты и правила ротации логов.
- Rate limit на login/API, проверка HTTP security headers и отсутствия
  чувствительных данных в access/error logs.
- Процедура отключения организатора и восстановления/ротации компрометированных
  кодов.
- Зафиксировать целевые версии Python/Node, зависимости и автоматическую CI
  проверку тестов/build/lint.
